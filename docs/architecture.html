What it actually does

Scope, and the things it deliberately isn't

Kassepris is a deal aggregator, not a catalogue. It holds only the products that appear in this week's offers, at the specific physical stores a shopper has selected. Everything else about a supermarket's assortment is out of scope.

It runs as a batch job that starts, finishes and exits — weekly on AWS Fargate — not as a server. And despite living in a folder called supermarket-scraper, almost nothing here scrapes rendered HTML: every chain is reached over plain HTTP, through the same endpoints their own websites call.

  • Only stores and chains are precious. Product and offer data is disposable — it re-fetches in fifteen minutes. Store metadata and geo enrichment does not.
  • One barcode, one row, across all three chains. That is what turns "cheapest price" into a plain SQL join rather than a matching problem at read time.
  • Money is integer öre. Never a float, anywhere in the schema.
  • Politeness is only what a chain actually declares. No invented delays — see Environments & limits.

The two flows

There are exactly two — everything else is supporting code

Setup — run once per database

Creates the schema and loads the stores. Stores rarely change, so this is deliberately not on a schedule. One command: npm run db:init.

The weekly job — fetch, normalize, load

This is the recurring one: npm run products:update-all. Three stages, and the split between them is load-bearing.

Why three stages and not one

Fetching is slow and fragile — roughly 2,000 HTTP calls against three rate-limited third parties. Normalizing and loading are fast and pure. Keeping the raw responses on disk between them means you can re-run normalize and load a hundred times while debugging without touching the retailers again.

Three chains, three shapes

Same output, wildly different request patterns

All three fetchers write the same normalized shape. How they get there has almost nothing in common — which is why the file counts differ by three orders of magnitude.

Coop

728 stores · 10 concurrent · no cache limit

Calls Coop's own offers JSON API, the same one their website uses. Needs two public subscription keys lifted from Coop's frontend bundle — public, not secrets, but kept in .env for hygiene.

ICA

1283 stores · 3 concurrent · 850 ms floor

No API — but ICA server-renders every offer into a window.__INITIAL_DATA__ blob, so one plain GET per store gets everything. The slow chain, and the reason the job takes a quarter of an hour.

Willys

252 stores · 2 assortments · per category

The most involved fetcher. Fetches per category because the plain response carries no category per product, and recovers barcodes by parsing them out of image URLs, validated by GS1 check digit.

When a fetch fails

Three independent recovery layers, deliberately not merged

Roughly two thousand requests against three third parties will fail in three distinct ways, and each gets its own mechanism. The layering is the point: each one only handles what escapes the one inside it.

A fourth failure mode has no retry at all, because retrying wouldn't help: silent schema drift. If Coop renames a price field, nothing errors — the pipeline just starts writing nulls. schemaCheck.js reduces each response to sorted path:type pairs and diffs them against a stored baseline, so drift surfaces as a warning instead of a column quietly emptying.

The data model

Ten tables, three lifetimes

There are deliberately no retailer-specific tables — no ica_products, no coop_offers. Which chain a row came from is expressed only through stores.chain_id. The distinction that actually matters is lifetime: what persists forever, what is replaced every week, and what is kept only for history.

TableLifetimeHolds
chainsPersistentCoop, ICA, Willys — identified in code by a stable slug
storesPersistentOne physical shop. Unique on (chain_id, external_id) — a retailer's store id is only unique within its own chain
categoriesPersistentThe 11 normalized categories. The app never sees a raw retailer category
product_groupsPersistentThe user-facing "one search result". Carries the category — not products
productsPersistentOne SKU, keyed globally by GTIN, shared across every chain that sells it
store_productsPersistent"We have observed this product at this store", with first and last seen
offersCurrent weekOne deal at one store. Integer öre, plus a per-unit comparison price range
offer_productsCurrent weekWhich SKUs a mix-and-match deal covers — why there is no product_id on offers
historical_offersArchivePrevious cycles, copied verbatim before deletion
historical_offer_productsArchiveThe frozen eligibility of a past offer

Why a group holds many products. A "3 för 59 kr" campaign spanning chorizo, grillkorv and bratwurst is one group with three products and one offer. That is also why eligibility lives in offer_products rather than a column — an offer genuinely applies to a set.

Environments & limits

Only what each chain actually declares

APP_ENVDatabaseFetch pacing
developmentLocal PostgresFast — no politeness delay
testThe throwaway Postgres on 5433Fast, except ICA's hard floor
productionAWS RDS, SSL onHonors every declared limit

The rule is that no delay is invented. Each number below traces to something the chain itself publishes:

ChainDeclaresWhat we do
CoopNothing — no Crawl-delay, no RateLimit headers0 ms, every environment
ICA72 requests / 60s via RateLimit-* headers850 ms floor, adapting live
WillysCrawl-delay: 10 in robots.txt10,000 ms in production only

ICA's limit is the one that is genuinely enforced — exceeding it gets the IP blocked with a 403, so it holds even in test. That single constraint is most of the job's fifteen minutes. Willys' is a politeness request rather than a block, so development and test leave it at zero for iteration speed.

The known problem

Product identity, currently being redesigned

One part of the model is understood to be wrong, and it is the part everything else rests on. products.gtin is a single NOT NULL UNIQUE text column holding whatever string the retailer sent, and it is being asked to mean three different things at once.

Three failures in one column

Same barcode, different widths. A GTIN legitimately appears as 8, 12, 13 or 14 digits depending on who reports it. Compared as raw strings, one physical product becomes two rows — Nutella arrives as 80177173 from ICA and 00000080177173 from Willys, silently breaking the "one barcode, one row" premise the whole comparison depends on.

No-GTIN products vanish. The strict rule skips any product without a recoverable barcode. Those are real, shoppable deals — 53 products and 7,598 store-offers from Coop alone. The decision made is to keep them, with a chain-scoped fallback identity, flagged as not comparable.

Having a barcode isn't the same as being comparable. Roughly 8% are GS1 restricted-circulation codes: valid check digits, but minted in-house for weighed and counter goods, meaningful only inside one retailer — sometimes inside one store. ICA's in-store bakery mints a different code per store for the same cookie. So gtin IS NOT NULL is the wrong comparability test.

The full problem statement, the evidence behind each claim, and the validated normalizer that a fix should reuse live in docs/product-identity.md. Worth reading before touching anything barcode-shaped.

Note that the schema's own comments still describe the current strict-GTIN rule as correct. That contradiction is real and unresolved — the schema documents what is built, the design doc documents what is wrong with it.
